## Регулярное обновление

На новой машине сначала восстановите сырые данные последнего снимка (тогда страницы контрактов завершенных лет
не скачиваются повторно):

```bash
make install download-raw
```

Затем:

```bash
make catalog fetch contracts build docs test
git add -A && git commit -m "data: update to $(date +%F)" && git push
make release            # a new data-<collection date> release with the database, Parquet and raw data
```

* `catalog` читает стартовую страницу и формы каждого отчета за каждый год: годы, списки классификаторов с кодами,
  документы PDF (`data/catalog/site.json`, `data/catalog/classifiers/*.json`, `data/catalog/documents.json`).
  Изменения видны в `git diff` — удобный способ заметить, что на сайте что-то изменилось. Шаг также проверяет, что
  варианты «группировать по» по-прежнему имеют ожидаемые подписи (`warnings` в `site.json`).
* `fetch` выполняет каждый запрос отчета за каждый год (≈15 запросов + пробные запросы на год, всего 10–30 минут:
  полное дерево расходов формируется до 5 минут). Пробные запросы выполняются повторно вместе со своим деревом,
  поскольку сопоставляются по суммам. Шаг можно сузить: `python -m arm_budget fetch --report revenue --years 2026`.
* `contracts` скачивает страницу договоров каждой строки расходов с договорами (≈2 000–2 300 в год; большинство
  ≈1 с, страницы строк с тысячами договоров — минуты; ≈3–5 часов на три года). Страницы, уже имеющиеся на диске,
  сохраняются, кроме последнего года (`--refresh-years 1`), договоры и платежи по которому меняются каждый день:
  его страницы скачиваются заново, если они старше 12 часов (`--max-age-hours`). Манифест записывается каждые
  100 страниц, поэтому прерванный запуск продолжается с места остановки; страница, не ответившая за 45 с (две
  попытки), запрашивается снова в следующем проходе (до трех проходов); `--force` скачивает всё заново.
* `build` пересоздает всю базу данных (≈1 минута) и выводит `qc_summary`; `docs` заново генерирует
  `docs/data_dictionary.md` и `docs/*/inventory.md`.
* Проверьте `SELECT * FROM qc_summary` (см. [data_quality.md](data_quality.md)). Если `missing_translation` имеет
  статус `warn`, переведите новые названия (см. [translations.md](translations.md)) и пересоберите базу.
* `release` требует чистого рабочего дерева и отправленного `HEAD` (тег релиза ставится на этот коммит), а также
  `gh` с правом записи в репозиторий. Тег по умолчанию — `data-<дата последнего запроса отчета>`.

Рекомендуемая частота: ежемесячно; как минимум один раз в январе–феврале, до того как сайт удалит самый старый год
(сайт хранит три года; релизы этого репозитория — единственный архив более старых лет).

## Когда появляется новый год

Сайт добавляет новый бюджетный год в начало списка лет, поэтому индексы `SITE_YEAR` остальных лет меняются
(`1` — всегда последний год). Сборщик читает соответствие из формы при каждом запуске `catalog`, так что
в коде ничего менять не нужно. Самый старый год исчезает с сайта: сохраните его сырые данные (архивы релизов),
если они нужны для последующих сборок — сборка использует только то, что находится в `data/raw` и `data/catalog`.

Ожидайте много новых названий (программы, счета, строки дефицита): переведите их (см. выше).

## Что делать, если…

**Запрос завершается ошибкой или зависает.** Сервер сбрасывает долгие соединения, а иногда удерживает запрос без
ответа. Клиент повторяет каждый запрос (5 попыток с увеличивающимися паузами), использует новое соединение для
каждого запроса и имеет тайм-ауты чтения 120 с (400 с для страниц результатов, `config.HTTP_RESULT_TIMEOUT`).
Запрос, результат которого не содержит таблицы или имеет неожиданную группировку, повторяется в новой сессии.
Запустите шаг снова — для контрактов он продолжит с места сбоя; отчеты всегда запрашиваются заново.

**Коды не определены** (`qc_unresolved_code`). Пробные запросы не нашли код для подписи. Посмотрите на подпись в
`stg_report_node` и на список классификатора за этот год (`data/catalog/classifiers/<report>_<year>.json`). Обычно
сайт что-то переименовал; повторный запуск `fetch` для этого года/отчета заново выполняет пробные запросы (до трех
раундов по 5, 20 и 60 наиболее похожих кодов, расширяя набор кодов-кандидатов). Если у подписи вообще нет
соответствия в списке, строка остается без кода; суммы при этом остаются в фактах.

**Изменились подписи группировки** (`warnings` в `data/catalog/site.json` или запрос завершается ошибкой
`grouping … != …`). Обновите `group_value` / `group_label` измерений в `src/arm_budget/config.py`.

**В формах появился новый вид доходов, представление дефицита или отчет.** Параметры записываются в
`data/catalog/classifiers/*.json` (`selects`); добавьте их в `config.REVENUE.extra` / `config.DEFICIT.extra` или
новый `Report` в `config.py` и соответствующий разбор в `build.py`.

**В отчете о дефиците появился новый стиль нумерации.** Структура выводится в `parsers/deficit.py`
(регулярные выражения для `Ա.`, `1.`, `1.1`); нераспознанные строки становятся строками `detail`.

**Изменилась верстка страницы.** Все парсеры небольшие и покрыты тестами с фикстурами (`tests/test_parsers.py`):
таблица (`parsers/grid.py`), формы (`parsers/forms.py`), контракты (`parsers/contracts.py`), экспорты
(`parsers/xls_export.py`).

## Устройство кода

| модуль | роль |
|---|---|
| `config.py` | пути, URL, настройки HTTP, определения отчетов и классификаторов |
| `site.py` | клиент сайта: сессия, форма, запрос, результат, экспорт, контракты; повторы |
| `fetch.py` | шаги `catalog`, `fetch`, `contracts`; манифесты в `data/catalog` |
| `tree.py` | превращает сгруппированную таблицу в дерево узлов (и плоский список строк контрактов) |
| `resolve.py` | коды классификаторов по названию и по пробным запросам (используется в `fetch` и `build`) |
| `build.py` | собирает базу данных DuckDB |
| `translations.py`, `translit.py`, `reference.py` | словари, транслитерация, статические трехъязычные справочные данные |
| `docs.py`, `release.py` | генерируемая документация, снимки данных в релизах GitHub |
